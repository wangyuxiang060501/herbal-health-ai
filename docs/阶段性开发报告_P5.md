### 2.2 集成测试（6.1.2）

`tests/test_integration_flow.py`，**只走 HTTP**，验证"各层装配起来之后还对不对"。  
覆盖三条主线：主链路（问卷→判定→推荐→历史→趋势）、异常分支（急症截断、追问、非法 id）、  
数据一致性（概况数字与列表数字对得上）。

**这一轮测试挖出了两个真实缺陷**，都不是测试写错，是代码有问题：

#### 缺陷 1：详情接口没有免责声明

`POST /consultation/start` 会返回 `disclaimer`，但 `GET /consultation/{id}` 不返回。  
而前端结果页读的正是详情接口 —— 用户刷新结果页就看不到免责声明了。  
免责声明是安全层"不可缺失"的输出，这是真漏。

修法：在 `consultation_detail()` 里用常量 `sg.DISCLAIMER` 兜底。  
声明内容是固定合规文本、不随个案变化，所以取常量而非落库。

#### 缺陷 2：写接口与读接口返回的推荐结构不一样

`/start` 返回 `recommend.herbs`（`_build_recommend()` 的成品），  
而详情接口返回的是落库的原始 `herbs` 字典，键是 `candidates`。  
同一个业务对象在两个接口里长得不一样，前端详情页取 `recommend.herbs` 就是空的。

修法（两步）：落库改为存标准形态；同时加 `_normalize_recommend()` 读时兼容历史数据  
（否则升级前已存在的老记录会读不出推荐）。

### 2.3 安全测试（6.1.3）

`tests/test_security.py`，测的是"**被攻击时会不会破防**"：

| 攻击面                 | 防线                               | 结果               |
| ------------------- | -------------------------------- | ---------------- |
| SQL 注入（4 种 payload） | ORM 参数化 + 分页校验                   | 不报错、表未被删 ✅       |
| XSS（4 种 payload）    | 前端不用 `v-html`（架构测试锁死）+ 后端剥离可执行片段 | ✅                |
| 提示词注入（4 种）          | **安全层在 LLM 之外**                  | 附子/朱砂/雄黄无法进入推荐 ✅ |
| 医疗术语                | 输出侧强制过滤 + 免责声明不可删                | ✅                |

两条值得单独说：

1. **「前端不得使用 v-html」是一条架构测试**。  
   只要有人为了"富文本效果"加一个 `v-html`，这条就红。  
   它比任何后端过滤都可靠——后端过滤总可能被绕过，而"根本不渲染 HTML"绕不过去。
2. **后端补了 XSS 剥离**（`sanitize_html`）。立场写清楚：**不做全量 HTML 转义**  
   （前端 `{{ }}` 已转义，再转一遍用户会看到 `&lt;` 这种脏文本），  
   只剥离 `<script>` 块、`on*=` 事件处理器、`javascript:` 协议三种"一旦渲染就执行"的构造。  
   这是纵深防御，主防线仍是前端不渲染 HTML。

### 2.4 性能测试（6.1.4）

`scripts/bench_api.py` —— **起真实 uvicorn 进程再并发打**，  
把 uvicorn 调度、SQLite 连接竞争、GIL 争用都算进去（用 TestClient 在进程内跑会偏乐观）。

## 三、6.2 优化

### 3.1 并发 500 的根因与修复（6.2.2）—— 本轮最大收获

首次压测：**97/100 成功，3 次 HTTP 500**。翻服务端日志，是  
`sqlite3.OperationalError: database is locked`。

SQLite 默认配置下，一个写事务会锁住整库，且拿不到锁时**立即报错**而不是等待。  
所以修法是两条 PRAGMA：

```sql
PRAGMA journal_mode = WAL;   -- 读写不再互斥
PRAGMA busy_timeout  = 8000; -- 拿不到锁先等 8s
```

主库（SQLAlchemy connect 事件）和 **LangGraph Checkpointer**（它每个节点都写快照，  
是第二个锁来源）都加上了。

效果：

|     | 修复前           | 修复后            |
| --- | ------------- | -------------- |
| 成功率 | 97/100（3×500） | **100/100**    |
| p50 | 1129 ms       | **395 ms**     |
| 吞吐  | 8.5 req/s     | **11.1 req/s** |

这条已用 `tests/test_performance.py` 锁死（断言 WAL 与 busy_timeout 必须开着），防止被改回去。

> **论文价值**：这是一个有"前后对比"的真实优化案例——不是"我加了索引所以更快"，  
> 而是"压测发现 3% 请求 500 → 定位到 SQLite 写锁 → 改两条 PRAGMA → 100% 成功"。

### 3.2 索引（6.2.2）

新增 5 个索引，覆盖"按时间倒序取最近 N 条"和"取整段对话"这两类高频查询：

- `consultations`: `created_at`、(user_id, created_at) 复合
- `messages`: (consultation_id, round_no) 复合
- `safety_logs`: `created_at`、`rule`

⚠️ 一个容易忽略的点：`create_all` **只建缺失的表，不会给已有表补索引**。  
所以另写了 `_migrate_add_indexes()`，用 `CREATE INDEX IF NOT EXISTS` 幂等补齐老库。

### 3.3 缓存（6.2.1）—— 没上 Redis，理由写清楚

清单写的是"Redis 缓存优化"。**我改成了进程内 TTL+LRU**，理由：

| 维度   | Redis   | 进程内                         |
| ---- | ------- | --------------------------- |
| 部署   | 需多起一个服务 | 零依赖                         |
| 缓存内容 | —       | 只缓存聚合统计（类别/归经/数据集概况），条目数个位数 |

为这点数据引入 Redis，收益远小于运维成本。而且 `ttl_cache` 是装饰器形态，  
将来要多实例部署，**只换实现，调用方一行不改**。

实现中踩的坑：**缓存键把 Session 算进去了** —— 每个请求都是新的 Session 对象，  
键必然不同，命中率恒为 0，看起来"加了缓存"其实一次没命中。  
所以加了 `ignore_types` 参数排除 Session，并写了专门的用例防回归。

另外 `GET /api/v1/meta/cache` 暴露命中率——**没有命中率的缓存等于没加**。

### 3.4 前端优化（6.2.3）

`vite.config.js` 加 `manualChunks`，按"是否首屏必需"拆四包：  
`echarts`（~1MB，只有结果页和"我的"页用）、`html2canvas`（保存图片时才用）、  
`vant`（很少变，利于长缓存）、`vue` 全家桶。

### 3.5 SSE 连接管理（6.2.4）

`useSSE` 加了两个能力，设计上有个关键取舍：

- **空闲超时 45s**：判据是"距上次收到数据"，不是总耗时。  
  因为 LLM 推理本来就慢，但慢也会一帧一帧吐字——**慢不等于卡死**。
- **断线重连**：只在**还没收到任何数据时**重试（最多 1 次）。  
  **收到数据之后断开一律不重放**——否则用户会看到两次结果，后端还会产生重复问诊记录。

这个取舍有用例锁死：`已经收到数据后断开，绝不重放请求`。

## 四、6.3 部署

7 个配置文件：

| 文件                        | 作用                                          |
| ------------------------- | ------------------------------------------- |
| `backend/Dockerfile`      | 构建期生成知识库切片；运行时数据挂卷；HEALTHCHECK 复用 `/health` |
| `frontend/Dockerfile`     | node 打包 → nginx 托管；内置 SPA 回落配置              |
| `docker-compose.yml`      | 开发版：Vite dev server + uvicorn --reload      |
| `docker-compose.prod.yml` | 生产：backend + frontend(nginx) + certbot      |
| `deploy/nginx.conf`       | 静态文件 + `/api` 反代 + HTTPS                    |
| `deploy/init-ssl.sh`      | HTTP-01 申请 Let's Encrypt                    |
| `deploy/部署手册.md`          | 完整操作步骤 + 上线检查清单                             |

两个设计要点：

1. **backend 不暴露宿主机端口**，只能由 nginx 走容器内网访问 —— 少一个攻击面。
2. **Nginx 对 `/api/` 必须 `proxy_buffering off`**，否则 SSE 流式输出会被攒成一坨，  
   前端的打字机效果变成最后一次性弹出。**这是部署阶段最容易忽略的一处配置。**

**未执行**：6.3.4 域名备案（需本人身份材料 + 10–20 个工作日）、  
6.3.5 部署到云服务器（无可用服务器）。二者都写进了手册作为可执行步骤。
