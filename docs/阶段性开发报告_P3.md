## 二、知识库构建（4.1）

`scripts/build_kb.py` 把四类原始数据切成结构化切片，统一落 `data/kb/chunks.jsonl`：

| 切片类型 | 数量 | 来源 | 说明 |
| --- | --- | --- | --- |
| `herb:*` | 604 | `tcm_828_herbs.json` 去重后 | 查询层药材，可检索但不可入膳 |
| `food:*` | 106 | `food_medicine_106.json` | 药食同源目录，推荐层唯一合法来源 |
| `constitution:*` | 9 | 九种体质 | 含「常见症状与体感」注入 |
| `symptom:*` | 11 | 症状→体质映射 | 桥接用户口语与知识库术语 |
| `safety:*` | 4 | 黑名单/配伍禁忌/特殊人群 | 安全规则也可被检索到 |

切片一律带 `chunk_id / source / metadata`，**这是引用回溯能成立的唯一前提**——
没有稳定 id，后面「这句依据哪条知识」就无从谈起。

> ⚠️ 论文口径提醒：`herb:*` 是 **604 味唯一药材**，不是 828 条原始记录
> （828→604 的去重依据见 `docs/数据去重报告.md`）。论文里不要写「828 味药材知识库」。

## 三、三档 embedder 与两档向量库（4.2）

全部做成**端口 + 多实现 + 自动降级**，缺任何依赖都不影响系统启动（ADR-005）。

| 组件 | 实现 | 状态 |
| --- | --- | --- |
| Embedder | `sentence-onnx`（真语义，需本地 ONNX 模型） | 未装模型，自动跳过 |
| | `tfidf-char`（scikit-learn） | 未装，自动跳过 |
| | **`hashing-bigram`**（零依赖，512 维） | **当前实际使用** |
| VectorStore | **`chroma`**（chromadb 1.5.9，持久化） | **当前实际使用** |
| | `memory`（纯内存 + JSONL 落盘） | 降级档 |

两个实现上的坑，都踩过并修掉了：

1. **hashing 必须确定性。** Python 内置 `hash()` 每次进程随机加盐，
   索引时和查询时算出的向量会不在同一个空间。改用 md5 做稳定散列。
2. **索引向量必须和 embedder 状态绑定。** TF-IDF 的 vocabulary / IDF 是 fit 出来的，
   只存向量、查询时新 fit 一个，检索结果会全错。所以 hashing 的 IDF 设计成可 JSON 序列化，
   且只在 `count()` 对得上时才复用已有向量库。

## 四、混合检索（4.3）—— 本轮最关键的一个判断

### 4.1 问题：hashing 是「字面相似」，不是「语义相似」

用户说「怕冷」，知识库里写的是「畏寒」。纯向量检索的实测 top3 是：

```
查询「怕冷手脚冰凉」
  语义通道 top3：['herb:使君子', 'herb:黄连', 'symptom:手脚冰凉']   ← 前两条是噪声
  关键词通道 top3：['constitution:阳虚质', 'symptom:畏寒怕冷', 'symptom:手脚冰凉']  ← 准确
  融合后  top3：['symptom:手脚冰凉', 'constitution:阳虚质', 'symptom:畏寒怕冷']
```

「使君子」「黄连」跟「怕冷」毫无关系，纯粹是字面 n-gram 撞上了。
**这说明在离线降级档下，语义通道不可信。**

### 4.2 解法：BM25 关键词通道 + 同义词扩展 + RRF 融合

- **同义词表**（`hybrid.SYNONYMS`，26 组）：怕冷→畏寒/阳虚、失眠→不寐、没力气→乏力/气虚…… 
  只做**单向归一到知识库用语**，不做自由联想，避免引入错误召回。
- **BM25**：term 用字符 bigram，k1=1.5、b=0.75。
- **RRF 融合**：`score(d) = Σ w_i / (60 + rank_i(d))`。
  只依赖排名，天然规避「余弦 0.3 和 BM25 8.7 怎么加权」这个没有物理意义的问题。
- **权重按 embedder 能力给**（`indexer._weights()`）：hashing/tfidf 档下语义权重降到 **0.4**、
  关键词 **1.0**；真语义模型才两路并重 1.0/1.0。

### 4.3 自检结果（4.5.1）

```
✓ 怕冷手脚冰凉    → top1=constitution:阳虚质
✓ 总是觉得没力气   → top1=symptom:乏力疲乏
✓ 晚上睡不着      → top1=symptom:失眠
✓ 脸上容易长痘出油  → top1=symptom:长痘出油
✓ 皮肤容易出现淤青  → top1=constitution:血瘀质
✓ 附子能不能吃     → top1=herb:白附子
✓ 痰多身体沉重     → top1=symptom:肥胖痰多
自检通过 7/7
```

其中「晚上睡不着」最初是**失败**的——召回的是马尾连/穿山龙/苦楝皮。
根因是知识库里根本没有「失眠/不寐」的内容。补 `symptom_chunks()` 后通过。
**这个失败过程本身值得写进论文**：它证明了「检索做不好，先查知识库缺什么，而不是先调模型」。

`/api/v1/rag/explain` 可以打出两路通道各自的 top3 与融合结果，
论文里那张「语义 vs 关键词 vs 融合」的对比表就是它导出的，不是手编的。

## 五、上下文注入与引用回溯（4.4）

三个 LLM 节点的 Prompt 都加了 `context` 参数，注入【知识库检索结果】块，
并要求**用 `[n]` 标注出处、不得引入检索结果之外的知识**。

- 体质解读节点（`constitution.py`）：检索体质 + 症状切片
- 药材解读节点（`herb_match.py`）：检索药材切片
- 药膳节点（`food_recipe_node`）：检索食材切片，写入 `retrieved_evidence`

引用链条：`rag_citations` 进 `ConsultationState` → 落 `consultations.rag_citations` 列
→ `/consultation/{id}` 返回。前端结果页新增「知识依据」卡片，
解读里的 `[n]` 可点击跳到对应切片。

## 六、有/无 RAG 对比实验（4.5.3）

真实 LLM（本地 `qwen3:8b`），同一份输入跑两遍，唯一变量是 `RAG_ENABLED`。
完整输出见 `docs/RAG_有无对比.md`。

| 指标 | A 组（RAG 开） | B 组（RAG 关） |
| --- | --- | --- |
| 召回切片数 | 7 | 0 |
| 引用标记 `[n]` 数 | **4** | **0** |
| 能在召回切片中找到出处的药材 | **1** | **0** |
| 不在 106 目录的品种 | 无 | 无 |

两点值得注意：

1. **引用标记 4 vs 0** —— 这是 RAG 生效最硬的证据：A 组每句结论后面都挂了出处编号。
2. **A 组说「大枣」，B 组说「红枣」** —— 「大枣」是 106 目录的规范别名，
   「红枣」是口语称呼、根本不在目录里。RAG 顺带把模型的用词拉回了目录口径。
   这条虽然不在预设指标里，但对「推荐可落地」是有意义的。

**指标局限（论文里必须如实写）**：药材检出基于「106 目录 + 604 味药材」词典的字符串匹配，
像「红枣」这类未收录的口语称呼不在检测范围内；且本地 8B 模型单次采样存在波动，
结论应表述为「本实验条件下」，不宜外推。

## 七、顺带修掉的一个真实缺陷：白名单别名误杀

做 A/B 时发现「大枣」被判为**不在** 106 目录。查下去是个真问题：

目录里有两种括号，语义完全不同——

- **别名型**：`姜（生姜、干姜）`、`枣（大枣、酸枣、黑枣）`、`龙眼肉（桂圆）`
- **限定型**：`杏仁（甜、苦）`、`肉苁蓉（荒漠）` —— 括号里是规格，不是别名

原实现只取括号前主名，于是「大枣」「干姜」「桂圆」全被判为「非药食同源品种」而拦掉。
这是安全闸的**假阴性（误杀合法药材）**，不是安全，是漏推荐。

修法：别名必须由数据源显式给出（`alias` 字段，35 条有值），
**只有 alias 非空时才额外解析括号**——这样「荒漠」「甜」「苦」不会被误当成别名。
同时保留「调用方不传 aliases 时退化解析括号」的兜底。

结果：别名 44 条，`大枣/酸枣/黑枣/生姜/干姜/桂圆` 全部命中，
`附子/半夏/柴胡` 仍被正确拒绝，`荒漠/甜/苦` 未被污染。
新增 5 个测试锁死这个边界（含「扩别名不得放松安全边界」）。
规则表 59 味药材经复核全部仍通过，说明此前未造成实际误杀。
