## 三、四个值得说明的实现决策

### 3.1 SSE 必须自己实现：原生 EventSource 不支持 POST

后端的流式接口是 `POST /api/v1/consultation/stream`（要带问卷与主诉），而浏览器原生
`EventSource` 只能发 GET。因此 `src/composables/useSSE.js` 用 `fetch + ReadableStream` 手工解析 SSE 帧。

这里有个容易踩的坑：**网络分块边界不等于帧边界**，一个 SSE 帧可能被切成两块到达。
实现里用缓冲区按 `\n\n` 切帧，并专门写了「跨帧粘包」用例锁死这个行为。

节点级 `node` 事件直接驱动进度条——**进度是后端真实节点执行产生的，不是前端伪造的假进度**。

### 3.2 业务码必须解包：急症拦截返回的是 HTTP 200

后端的业务异常（急症拦截 40301、安全拦截 40302）**以 HTTP 200 返回**，只在响应体
`{ code, message, data }` 的 `code` 字段体现。如果前端只看 HTTP 状态码，急症场景会被当成成功，
用户就看不到"请立即就医"的红色警示。

Axios 响应拦截器统一解包业务码并抛出带 `code` 的错误，页面据此弹警示对话框而不是通用 Toast。

### 3.3 问卷不硬编码：题面全部来自后端

27 道题的题干、核心题标记、1–5 级评分标签（没有/很少/有时/经常/总是）全部取自
`GET /api/v1/meta/questionnaire`。这样 **GB/T 46939—2025 标准原文拿到后替换后端 `questionnaire.py`，
前端无需改动**。

### 3.4 安全能力要被"看见"，不能只是后端拦了

两个地方把后端的安全能力显式呈现出来：

- 药材详情页：对当前药材真实调用 `safety/probe-herbs`，查「附子」会显示"不得进入药膳方案"及替换品种；
- 结果页：展示被安全层拒绝/替换的品种记录。

答辩时这两处可以直接演示"系统确实拦得住"。

## 四、环境踩坑（本机特有，已记录到 frontend/README.md）

1. **esbuild 无法删除系统 TEMP 文件**：构建报
   `[vite:esbuild-transpile] remove ... Access is denied`。
   解法：把 `TMP`/`TEMP` 重定向到项目内 `.tmp/` 再构建（代码本身没问题，只是清理步骤失败）。
2. **vitest 5 与 vite 5 依赖冲突**：`npm i -D vitest` 直接 ERESOLVE 失败，需锁 `vitest@^2.1.8`。
3. **npm 11 默认拦截 lifecycle scripts**：esbuild 需要 `npm approve-scripts esbuild`。
4. **浏览器自动化不可用**：agent-browser 的 Chrome 已安装成功，但 daemon 启动 6 分钟无响应，
   按 fail-fast 原则放弃，改用组件挂载测试自证运行时正确性。

## 七、遗留风险（与 P0/P1 相同，仍未消除）

1. **106 味药食同源白名单仍是初稿**（9 字段全 `verified=false`）。
   这是安全关键数据，禁忌/人群标错会直接造成风险，需逐条对照《中国药典》核验。
2. **GB/T 46939—2025 标准原文未获取**。当前问卷题面按九种体质通行表述编写，
   拿到原文后只需替换 `backend/app/domain/constitution/questionnaire.py`，计分算法与前端都不用改。
3. **828 这个数字不要当作品种数**：原始 828 条记录去重后唯一药材 604 味，
   另有 22 味由法定目录补齐，合计 626 味。论文与答辩 PPT 需按这个口径表述。
