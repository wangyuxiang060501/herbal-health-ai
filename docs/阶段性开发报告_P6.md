## 一、用户认证（5.4.1）

### 1.1 后端 `/api/v1/auth`

| 接口 | 说明 |
|---|---|
| `POST /auth/register` | 手机号 + 密码注册，**注册即登录**（直接返回令牌对）；重复手机号 400 |
| `POST /auth/login` | 登录；失败统一话术「手机号或密码错误」（HTTP 401），**不暴露手机号是否存在**（防枚举，有测试断言） |
| `POST /auth/refresh` | **旋转刷新**：每次签发全新令牌对，旧 refresh 自然作废 |
| `GET /auth/profile` | 需登录（`get_current_user` 强制依赖） |

### 1.2 安全选型（论文可直接引用）

- **bcrypt 直调官方 API**，不用 passlib（1.7.4 与 bcrypt≥4.1 不兼容）；口令只存 `$2` 前缀散列，测试断言明文不落库、不回显。
- bcrypt 72 字节截断问题：`hash_password` 显式拒绝超长口令，而不是静默截断（截断会让超长口令冲突为同一口令）。
- **JWT 双令牌（HS256，PyJWT）**：access 2h（短寿命压小泄露窗口）+ refresh 14d；claim `typ` 区分，refresh token 访问业务接口一律 401（有测试）；claim `jti` 保证同秒签发的令牌不同（旋转可观测 + 为吊销列表预留锚点）。
- HMAC 密钥长度：默认开发密钥补足到 ≥32 字节（RFC 7518 §3.2），PyJWT 会告警短密钥；`.env.example` 提供 `JWT_SECRET_KEY` 独立配置项与生成命令。

### 1.3 数据隔离与向后兼容

- `get_optional_user` 可选依赖：**无令牌 = 匿名模式，行为与认证上线前完全一致**（既有 226 项测试零改动全绿）。
- 问诊 `/start` `/stream` 携带令牌时归属 `user_id`；历史/趋势接口三口径：登录看自己、匿名看 `user_id IS NULL`、内部调用不过滤。
- 隔离有专项测试：用户 A 的记录对 B、对匿名均不可见；趋势按身份隔离。

### 1.4 前端接入

- `api/tokens.js`：令牌持久化收敛点（避免 store ↔ api 循环依赖）。
- `api/index.js`：请求拦截器注入 `Authorization`；**401 → refresh 换新 → 重放原请求（仅一次）**，并发 401 用共享 Promise 合并防风暴；刷新失败清令牌退回游客。
- `stores/user.js`：真实 `login/register/syncProfile`，游客模式保留（`isLogin` 以 `userId` 为准）。
- `LoginView.vue`：**假验证码改为真实密码登录/注册**（原页面是演示态：验证码任意填、身份只写 localStorage，与本阶段后端能力已不匹配）。
- 校验方式：三个 JS 模块 `node --check` 通过；LoginView 以 `@vue/compiler-sfc` 完成模板+脚本编译校验（vitest 仍受本机 esbuild 故障阻塞，如实记录）。

## 二、Alembic 迁移（1.3.3 / 1.3.4）

- `backend/alembic.ini` + `backend/migrations/`：`env.py` 直接注入**应用自身配置**（`settings.database_url`）与 **ORM 元数据**（`Base.metadata`），保证迁移视角与运行视角同源；SQLite 启用 `render_as_batch`。
- 首个迁移 `60a09271bd5b`：7 表 + 17 索引（含 6.2.2 的 `(user_id, created_at)` 复合索引）。
- **闭环实测**：空库 `upgrade head` → 7 表 + 17 索引 + version 表 → `downgrade base` 全清 → 再 `upgrade head` 恢复一致。
- 存量开发库（`var/app.db`）仍由 `init_db()` 托管，纳入迁移管理只需 `alembic stamp head`。
